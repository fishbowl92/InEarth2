# InEarth2 회고와 개선 방향

이 문서는 당시 코드를 현재 관점에서 검토한 내용입니다. 과거 코드를 현재 방식으로 개발한 것처럼 다시 작성하지 않고, 구현 경험에서 얻은 개선점을 기록합니다.

## 유지할 설계 판단

- 맵 생성 규칙을 `Maptile` 데이터로 분리한 점
- 전투와 이동이 공통 격자 상태를 사용한 점
- 연쇄 타격의 판정과 시각 효과를 순차적으로 연결한 점
- 반복 생성되는 이펙트를 비활성화 후 재사용한 점

## 현재 다시 구현한다면 개선할 부분

### 관리자 클래스 역할 분리

`MapManager`에 맵 생성, 전투 상태, UI와 이펙트 관리가 함께 들어 있습니다. 현재 다시 설계한다면 다음 책임으로 나눕니다.

- `MapGenerator`: 격자 생성 규칙
- `GridState`: 타일 상태 조회와 변경
- `CombatSystem`: 피해와 스킬 판정
- `EffectPool`: 이펙트 생성과 재사용
- `BattlePresenter`: UI와 애니메이션 표시

### 명시적인 타일 상태 사용

현재는 숫자 범위로 벽·아이템·몬스터·플레이어를 구분합니다. 이는 상태 규칙을 모르면 의미를 알기 어렵습니다. 현재라면 열거형과 별도 상태 구조를 사용해 의미를 코드에 드러냅니다.

### 문자열 기반 코루틴 호출 제거

`StartCoroutine("makeChainLight", data)` 형식은 함수명 변경을 컴파일러가 확인하지 못합니다. 현재라면 `StartCoroutine(makeChainLight(data))`처럼 함수 자체를 전달합니다.

### 테스트 가능한 순수 로직 분리

맵 생성 규칙과 다음 연쇄 대상을 찾는 로직을 `MonoBehaviour`에서 분리하면 Unity 실행 없이도 다음 항목을 단위 테스트할 수 있습니다.

- 동일한 시드에서 같은 맵이 생성되는지
- 맵 경계가 항상 막히는지
- 연쇄 대상이 없을 때 정상 종료하는지
- 재방문을 허용하는 스킬 규칙에서 이전 위치가 다음 대상 후보가 될 수 있는지
- 같은 위치를 반복 방문해도 연쇄 횟수 상한에서 종료하는지
- 다음 대상 소멸과 전투 종료 시 코루틴·이펙트가 안전하게 정리되는지

### 의미가 드러나는 전달 데이터

`TriggerData.ts`의 `x`, `y`, `z`는 호출 단계에 따라 좌표, 피해량, 연쇄 횟수와 스킬 번호로 해석됩니다. 짧은 이름이나 벡터 자료형이 이 용도에서 더 가볍다는 근거는 없습니다. 현재라면 `Damage`, `BounceCount`, `SkillIndex`처럼 의미가 드러나는 필드를 가진 별도 전달 구조로 바꾸겠습니다.

연출 루프의 진행 변수와 실제 도착 여부도 분리해 검사해야 합니다. 위 항목은 개선 제안이며, 이번 문서 정리에서 과거 게임 코드를 수정하거나 성능 차이를 측정한 것은 아닙니다.
